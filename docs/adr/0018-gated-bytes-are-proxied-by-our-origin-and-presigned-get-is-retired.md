# Gated bytes are proxied by our origin, and presigned GET is retired

**Every read of a stored object goes through our server.** ADR-0009 already proxied image bytes but kept PDFs on a presigned redirect, "where the browser navigates rather than embeds". The pdf.js research settled that the browser never navigates to a PDF — the viewer buffers the bytes into `getDocument({ data })` — so the redirect would have been a cross-origin `fetch` against garage, needing read CORS on the bucket and leaving `no-store` and `nosniff` as garage's headers to set rather than ours. That part of ADR-0009 is superseded: **PDFs are proxied too.**

Once the server streams the body it is holding the credentials, so it calls `GetObject` directly. **Presigned GET no longer exists anywhere in this design** — with it go the TTL choice, the expiry-mid-download problem, and read-side CORS. Bucket CORS narrows to `PUT`/`OPTIONS` for the upload path, which stays presigned (see ADR-0019). The cost is up to 25 MB per view through the app server, which the scope posture accepts.

**There are two byte routes, never one.** `/v/$slug/bytes/$documentId` serves visitors: it validates the visit cookie, loads the visit from Redis, checks `gate_version`, checks the link is active and unexpired, and checks the document is reachable from that link's target. **Reachable** is defined by ADR-0058: a document is reachable from a link when it is the link's target, or a member of the target vault, or *referenced* by one of those documents — one hop, read from `document_reference`, never transitive. Without that last clause an image embedded in a shared markdown document is unservable, and the visitor sees a broken image the owner cannot reproduce. `/api/documents/$documentId/bytes` serves the dashboard behind `orgMiddleware`, scoped by the branded `OrganizationId` of ADR-0011. Neither route falls back to the other's credential — a single handler branching on which credential it happened to find is the exact shape of a leak. Both delegate to one `streamDocument` helper so their headers cannot drift apart. This makes four server routes rather than three; the rest of the server surface is still `createServerFn`.

**Response headers.** `Content-Type` comes from `document.mime_type` — the sniffed value in our database, never what garage echoes back. `Range` is passed through to `GetObject` and `206`/`Content-Range` forwarded. There is **no `Accept-Ranges`**: its absence keeps pdf.js off the abort-then-range path, and the asymmetry with the forwarded `Range` header is deliberate. There is **no `ETag` and no conditional-request handling**: `no-store` leaves no cache to revalidate, and an `ETag` would hand a client a cheap way to confirm bytes still exist behind a revoked link. `connect-src 'self'` is written into the CSP explicitly, even though `default-src` already covers it, so the policy states the proxy decision rather than implying it.

**`Content-Disposition: attachment` is emitted only when `link.allow_download` is true.** That flag does three things and no more: it hides the Download button, it makes the byte route refuse the download parameter, and it hides pdf.js's own save and print controls. The bytes are in the browser either way. Viewer copy is neutral — "Downloading is disabled for this link", never "protected" or "secure" — and the owner's dashboard says plainly next to the toggle that it discourages rather than prevents.

**Refusing the download parameter is a `403`.** ADR-0032's query contract is: no parameter means inline and writes no Event; `?download=button` means attachment and a `download` Event with `{ via: 'button' }`. That is not the Dashboard route's `?download=1`. When `allow_download` is false, `?download=button` returns `403` and writes nothing — it does not silently downgrade to an inline stream. The word in this ADR was "refuse"; `403` is that word. A `pending` document still returns `409` and a missing object still returns `404`; neither appends an Event.

**The `download` Event is written after storage has returned a body and before the response is returned.** We cannot observe a body draining, so "after the transfer" is not available. A `409` or `404` therefore cannot have written a download.

**A visitor asking for bytes that are not there gets two different answers.** A `pending` document returns `409` and the viewer renders an uploading state with retry — it is true, it self-resolves, and one uploading document must not make a whole vault link look broken. A `ready` document whose object is missing returns `404` and logs loudly, because that is a real inconsistency and dressing it as "uploading" would hide it forever.

Rate limiting this route — a visitor can pull 25 MB repeatedly through our origin — belongs to the gate abuse policy, not here.

## Amendment: the visitor path is `/bytes/`, refusal is `403`, and the Event waits for a body

The original spelling `/v/$slug/f/$documentId` was a placeholder that never matched ADR-0032 or the route tree. The live path is `/v/$slug/bytes/$documentId`. "Refuse the download parameter" is a `403` with no Event, not a silent inline stream. The `download` Event is appended only after `GetObject` has returned a body, and never for `409` or `404`.
