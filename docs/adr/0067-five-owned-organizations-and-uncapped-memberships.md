# Five owned organizations, and memberships are uncapped

A user may run up to five organizations of their own, and belong to as many other people's as they are invited to. The two halves of that sentence are deliberately different: creating a tenant is a thing one person can do repeatedly and unilaterally, so it is capped, while being invited into someone else's requires that someone else to act, so it is not. Nothing in the product wants to tell a user they cannot accept an invitation because they already run five organizations of their own.

**Better Auth's `organizationLimit` cannot express this, and the number form expresses the opposite.** The option counts `listOrganizations(user.id)`, which is membership-based — organizations you merely joined count against your ability to create one. Setting `organizationLimit: 5` would therefore mean "you may be in five organizations", capping exactly the half we want uncapped. The option also accepts a function returning "has this user reached the limit", so we pass one that counts `member` rows where the user holds the owner role and compares against five. The default, worth stating because it is not what the docs imply, is unlimited: until this decision nothing capped anything.

**The cap is enforced at creation and deliberately not at promotion.** Better Auth consults `organizationLimit` in `createOrganization` and nowhere else — `updateMemberRole` never looks at it — so an owner of five can still be promoted to owner in a sixth by that organization's existing owner. We keep it that way rather than duplicating the check. The cap exists to stop one person spawning tenants, not to arbitrate who runs somebody else's; and capping promotion would let strangers' organizations consume a user's ability to create their own, which is a far stranger failure than an owner count of six.

The consequence is that the limit function performs a database read inside `src/server/auth.ts`. ADR-0011 already names that file as a sanctioned client import site — it is where the Drizzle adapter is constructed — so no fence moves and the count does not need a branded `OrganizationId`, being a question about a user rather than about a tenant.

**The cap arrives together with the way to reach it.** Creating an organization from the Dashboard lands in the same change, in the organization switcher, reusing `/onboarding`'s form and its slug-collision retry. A cap nobody can reach is not a policy, and the at-the-cap state is a present, disabled item that gives the reason rather than an item that silently disappears.
