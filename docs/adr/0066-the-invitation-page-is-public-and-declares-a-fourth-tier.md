# The invitation page is public and declares a fourth tier

An **Invitation** is delivered by email as an opaque id in a URL, and the person opening it is, at that moment, a stranger: they may have no account, or be signed in as somebody else. Better Auth's `getInvitation` is no help to that page — it requires a session whose email already matches the invitation, and it throws before returning anything otherwise. So the page that has to say "you have been invited to join Ferhat & Co" cannot get the organization's name from the endpoint whose entire job is reading invitations.

**We read the invitation ourselves, and that is a deliberate exception to ADR-0013.** A `createServerFn` takes the invitation id and returns the organization's name and the inviter's name. It returns nothing else: not the invited address, not the **Role** the invitation carries, not whether the invitation is pending or spent beyond the one distinction below. Putting the name in the emailed URL instead was rejected for being editable by the recipient before they forward it, and a signed token was rejected as a second credential format to maintain for one line of text. This does not widen ADR-0013's rule that organization administration belongs to Better Auth — every *mutation* still goes through `authClient`, and this is a read that Better Auth declines to serve.

## The page is a Gate wearing different clothes

An anonymous person holding an unguessable identifier, told who is asking and nothing about what is behind it, is exactly the shape ADR-0045 settled for the **Viewer**. So the invitation page shows a **Sender line** and inherits its rules verbatim, including the degradation to the organization alone — which is not hypothetical here, because Better Auth throws `INVITER_IS_NO_LONGER_A_MEMBER_OF_THE_ORGANIZATION` for an otherwise perfectly valid invitation whose inviter has since left.

**Expired is distinguished; canceled and fictional are not.** Better Auth collapses all three into `INVITATION_NOT_FOUND` — expiry is a timestamp comparison, and the row is never transitioned out of `pending` — but our own read can tell them apart, and it should. Somebody holding an expired invitation was genuinely sent it and learns nothing by being told it lapsed, whereas naming an organization for a canceled or invented id would disclose it to somebody who was never invited. Both messages offer the same single remedy, ask the organization for a new invitation, which is ADR-0047's rule applied off the Viewer. That rules out a resend button on the public page: it would let anyone holding a stale link generate mail to an address they cannot read.

**A signed-in stranger is told which account they are using, never which one was invited.** Better Auth's mismatch error names neither, and of the two the invited address is the one a forwarded link must not hand over. The user already knows their own address, so the half of the message worth printing is free.

## The public read declares a credential rather than escaping the audit

ADR-0012 buys auditability by making every permission check declarative, and `tests/pure/tier-coverage.test.ts` turns that into a sweep: every server function must name `authedMiddleware`, `orgMiddleware`, or a `permission(...)`. This function names none of them, and the sweep is right to fail it.

**So it declares an `invitationRecipient` middleware, and that name joins the tier set.** The middleware parses the invitation id, loads the invitation, and hands the handler the organization and inviter — nothing that names the recipient. This is the Viewer's precedent exactly: `gateCredential` exists so a Gate POST can state the credential it runs on instead of appearing untiered. The alternative was the by-name exemption list that already carries `src/routes/api/auth/$.ts`, and an exemption list is where the *next* unauthenticated function quietly joins; moving the file out of `src/server/functions` is worse still, because it makes the absence of a credential a property of a directory nobody audits.

There is no abuse counter on this read. The invitation id is a uuidv7 and unguessable, which is the same reasoning that lets a **Slug** stand as a public identifier on its own, and the endpoint discloses one organization name to whoever already holds the link.

## Accepting an invitation you no longer need is a success

`acceptInvitation` has no already-a-member check — it goes from the email match straight to an unconditional insert — and neither Better Auth's schema nor ours constrained one **Membership** per user per organization. Two member rows for one user would hand `orgMiddleware` two roles to choose from, which is precisely the corrupted state ADR-0010 insists must throw rather than resolve.

**A unique index on `member (organization_id, user_id)` closes it, and the accept flow checks first so the index is a backstop rather than the mechanism.** If the session user already holds a membership, we skip the accept call, set the organization active, and land them on the Dashboard: arriving where the link promised is the correct outcome, and an error page for "you are already in" would be a lie about a failure. The index then only fires on the genuine race, where a raw constraint violation surfacing from an endpoint we do not wrap is an acceptable price for never persisting an ambiguous role. This is not a new principle — ADR-0017 already says the database constrains the model — and what makes it worth recording is only that Better Auth ships without the constraint, so a reader will not find it in the plugin's schema.
