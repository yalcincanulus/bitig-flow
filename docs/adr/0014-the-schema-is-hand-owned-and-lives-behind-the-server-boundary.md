# The schema is hand-owned and lives behind the server boundary

**The Drizzle schema lives in `src/server/db/schema/`, split by concern, and exports flat.** ADR-0011 already made `src/server/db/` the only place the client is constructed and fenced it off with an oxlint `no-restricted-imports` rule; the schema belongs on the same side of that fence. Five files divide it — `auth.ts` (better-auth's owned tables), `content.ts` (`document`, `vault`, `vault_item`, `document_reference`), `sharing.ts` (`link`), `analytics.ts` (`visit`, `visit_event`), and `index.ts` re-exporting everything. The re-export is **flat and stays flat**: `defineRelations` does not accept nested schema objects on `1.0.0-rc.4`, and grouping exports under namespaces is the kind of tidying that breaks the relations graph in a way the error message does not explain.

**Column names come from `snakeCase.table`, not from hand-written SQL identifiers.** `drizzle({ casing: 'snake_case' })` was removed in the RC, so the mapping is per-table. Writing every name out — `text('storage_key')` — is sixty lines of noise that can silently disagree with the TypeScript key it sits beside. This is invisible to better-auth, which matches on **JavaScript property names** rather than SQL identifiers, so `userId` stays `userId` to the adapter while the column is `user_id`.

**The better-auth tables are hand-written and never gain a column of ours.** `auth@latest generate` emits `text('id').primaryKey()` with no default, which does not satisfy the `DEFAULT uuidv7()` constraint, and it overwrites its output file. So `auth.ts` is ours to maintain, and the generator is a thing to diff against when better-auth's version moves — which only works while the file contains nothing but better-auth's own columns. The moment one application column lands there, every future upgrade becomes a merge instead of a diff. Anything of ours that hangs off a **User** goes in one of our tables.

**Relations v2 covers the auth tables even though better-auth cannot use them.** One flat `defineRelations` spans the whole schema, including edges into `organization` and `user`, so our own `db.query` traversals work. Better-auth is handed an explicit `schema: { user, session, ... }` object of raw tables and `experimental.joins` stays **off** — its 1.6.28 adapter peers on `drizzle-orm@^0.45.2`, reads `db._.fullSchema` (which node-postgres no longer populates on the RC), and 500s against `defineRelations`. The two mechanisms coexist because they read different things: the adapter reads table objects, `db.query` reads the relations graph. Without that sentence written down, the auth edges in the relations file look like an oversight.

**Driver is `pg` (node-postgres); migrations are `generate` + `migrate`, never `push`.** The RC's behaviour was verified against the node-postgres driver specifically, and better-auth's adapter is exercised most heavily there. Migration folders under `./drizzle` are committed whole — `migration.sql` **and** `snapshot.json`, since the snapshot is the parent of the next diff. History stays linear: the RC's commutativity check goes exponential on merged snapshot DAGs.
