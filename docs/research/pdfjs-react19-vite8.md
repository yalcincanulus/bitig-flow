# pdf.js under React 19 / Vite 8

Research for [#6](https://github.com/veotaar/bitig-flow/issues/6). Scope: the **public viewer** — client-side pdf.js, per-page analytics via IntersectionObserver, short-lived (~60s) presigned GET after a gate. The public viewer uses server functions + route loaders, **not** TanStack DB collections. “Prevent download” is cosmetic and we say so.

**Stack in this repo (at research time):** React `^19.2.8`, Vite `^8.2.1`, TanStack Start. `pdfjs-dist` / `react-pdf` are **not** installed yet.

Sources are first-party: Mozilla pdf.js (repo, wiki, JSDoc generated from `src/display/api.js`), `pdfjs-dist` on npm, Wojciech Maj’s `react-pdf`, Vite 8 docs, W3C Intersection Observer and Beacon. Claims are cited. Random blog posts are not used as authority.

## 1. Package choice: `pdfjs-dist` vs `react-pdf`

### What Mozilla ships

Mozilla’s library is PDF.js. The npm artifact is **`pdfjs-dist`**: “a pre-built version of the PDF.js source code… automatically generated by the build scripts.” ([pdfjs-dist README](https://www.npmjs.com/package/pdfjs-dist); [mozilla/pdf.js README — “Using PDF.js in a web application”](https://github.com/mozilla/pdf.js/blob/master/README.md))

Latest `pdfjs-dist` at research time: **6.2.108** (published 2026-07-28). Entry is ESM: `"main": "build/pdf.mjs"`, types at `types/src/pdf.d.ts`. Worker lives next to it as `build/pdf.worker.mjs` (and a minified `.min.mjs`). The generic layout is `pdf.mjs` (display) + `pdf.worker.mjs` (core). ([pdfjs-dist@6.2.108 `package.json`](https://unpkg.com/pdfjs-dist@6.2.108/package.json); [Getting Started — File Layout](https://mozilla.github.io/pdf.js/getting_started/))

Mozilla’s website setup wiki: `npm install pdfjs-dist --save`. ([wiki: Setup PDF.js in a website](https://github.com/mozilla/pdf.js/wiki/Setup-pdf.js-in-a-website), last edited 2024-05-31)

### What `react-pdf` is

[`wojtekmaj/react-pdf`](https://github.com/wojtekmaj/react-pdf) is a **third-party React wrapper** around pdf.js (`Document` / `Page`), not Mozilla’s package. Current package **10.4.1**:

- **React 19 is a first-class peer:** `"react": "^16.8.0 || ^17.0.0 || ^18.0.0 || ^19.0.0"` (same for `react-dom`). DevDependencies pin React `^19.2.0`. README: “To use the latest version of React-PDF, your project needs to use React 16.8 or later.” ([packages/react-pdf/package.json](https://github.com/wojtekmaj/react-pdf/blob/main/packages/react-pdf/package.json); [packages/react-pdf/README.md — Compatibility](https://github.com/wojtekmaj/react-pdf/blob/main/packages/react-pdf/README.md))
- It **pins** `pdfjs-dist` to **`5.4.296`** (exact version, not a range). That is one major behind current Mozilla `6.2.108`. Mixing copies produces “The API version … does not match the Worker version …” ([package.json `dependencies`](https://github.com/wojtekmaj/react-pdf/blob/main/packages/react-pdf/package.json); discussed in [react-pdf #1581](https://github.com/wojtekmaj/react-pdf/discussions/1581) as a first-party maintainer explanation)
- Worker setup is still required; the wrapper does not remove the Vite worker problem. README recommended recipe is `pdfjs.GlobalWorkerOptions.workerSrc = new URL('pdfjs-dist/build/pdf.worker.min.mjs', import.meta.url).toString()`, set in the **same module** as `<Document>` / `<Page>`. ([README — Configure PDF.js worker](https://github.com/wojtekmaj/react-pdf/blob/main/packages/react-pdf/README.md))
- pnpm users may need to hoist `pdfjs-dist` (`public-hoist-pattern` / `publicHoistPattern`). Same README note.
- `Page` still renders a canvas (`renderMode` default `"canvas"`). Text layer default `renderTextLayer: true`. There is **no built-in virtualized page list** — you map `numPages` to `<Page>` yourself. ([README — Page props](https://github.com/wojtekmaj/react-pdf/blob/main/packages/react-pdf/README.md))

`react-pdf` is actively maintained (CI badge, v10.x docs, React 19 peers). It is compatible with React 19. It is **not** a substitute for understanding `workerSrc`, canvas sizing, or how `getDocument` fetches bytes.

### Recommendation (see also § Recommended shape)

For bitig-flow’s viewer (custom IO analytics, virtualization, presigned GET → in-memory bytes, TanStack Start client island), **add `pdfjs-dist` directly** and own a thin React wrapper. `react-pdf` would still need the same worker recipe, still pin an older pdf.js, and still leave page list / visibility / URL lifetime to us.

If a later prototype wants `Document`/`Page` scaffolding, pin **one** `pdfjs-dist` and never import both `pdfjs-dist` and `react-pdf`’s nested copy as two workers.

## 2. Worker setup under Vite 8

This is the recurring failure mode. pdf.js **parses in a Web Worker**. If the worker does not start, it falls back to a **fake worker on the main thread** (`warn("Setting up fake worker.")`) with worse jank. ([`src/display/api.js` `PDFWorker.#initialize` / `#setupFakeWorker`](https://mozilla.github.io/pdf.js/api/draft/api.js.html); source [`api.js` around the `new Worker(workerSrc, { type: "module" })` call](https://github.com/mozilla/pdf.js/blob/master/src/display/api.js))

### What `workerSrc` actually is

- Hello-world (Mozilla): “The workerSrc property shall be specified.” Then `pdfjsLib.GlobalWorkerOptions.workerSrc = "../../node_modules/pdfjs-dist/build/pdf.worker.mjs"`. ([`examples/learning/helloworld.html`](https://github.com/mozilla/pdf.js/blob/master/examples/learning/helloworld.html))
- If unset: `throw new Error('No "GlobalWorkerOptions.workerSrc" specified.')`. ([`PDFWorker.workerSrc` getter](https://github.com/mozilla/pdf.js/blob/master/src/display/api.js); [issue #10478](https://github.com/mozilla/pdf.js/issues/10478) — maintainers: always set it explicitly)
- The value **must be a string URL**. Assigning the imported worker **module object** is wrong; pdf.js then treats it as a failed real worker and uses the fake worker. ([PR #17504 — validate `workerPort`/`workerSrc`](https://github.com/mozilla/pdf.js/pull/17504))
- Generic builds construct: `new Worker(workerSrc, { type: "module" })`. ([`api.js` `PDFWorker.#initialize`](https://github.com/mozilla/pdf.js/blob/master/src/display/api.js))

So Vite must emit a **module worker file** whose **URL string** we pass to `GlobalWorkerOptions.workerSrc`. pdf.js constructs the `Worker`; Vite should not wrap it in a custom constructor unless we then pass `.url`.

### What Vite 8 documents

Vite’s **recommended** worker creation is `new Worker(new URL('./worker.js', import.meta.url), { type: 'module' })`. Detection only works if `new URL()` is **directly inside** `new Worker()`. Otherwise Vite treats it as a **static asset URL**. Query suffixes: `?worker` (constructor), `?worker&inline`, `?worker&url` (URL string of a worker chunk). Dev uses native module workers; production compiles the worker to a separate chunk (or inlines if asked). ([Vite Features — Web Workers](https://vite.dev/guide/features); [Vite Static Asset Handling](https://vite.dev/guide/assets.html))

`import x from 'file?url'` returns the public URL: `/src/...` in dev, hashed `/assets/...` in production. ([Vite — Importing Asset as URL](https://vite.dev/guide/assets.html))

`new URL('./img.png', import.meta.url)` is rewritten in production **only if the URL string is statically analyzable**. **“Does not work with SSR”** — `import.meta.url` differs in Node vs the browser. ([Vite — new URL(url, import.meta.url)](https://vite.dev/guide/assets.html))

### Recipes that match those facts

| Recipe | What Vite does | Fit for pdf.js `workerSrc` |
| --- | --- | --- |
| `import workerUrl from 'pdfjs-dist/build/pdf.worker.min.mjs?url'` then `workerSrc = workerUrl` | Asset URL (dev path → hashed prod file) | **Good.** String URL; pdf.js does `new Worker(url, { type: "module" })`. |
| `import workerUrl from 'pdfjs-dist/build/pdf.worker.min.mjs?worker&url'` | Worker chunk URL | **Good** if we only need the URL. Forces Vite’s worker pipeline. |
| `import PdfWorker from '...?worker'` then `new PdfWorker()` | Custom constructor | **Wrong for `workerSrc`.** That is not a string. Could be used as `workerPort` (`DocumentInitParameters.worker` / `PDFWorkerParameters.port`) — a different API. |
| `new URL('pdfjs-dist/build/pdf.worker.min.mjs', import.meta.url).toString()` | **Static asset URL**, not worker-constructor detection (because it is not inside `new Worker()`) | **Works in a client bundle** if Vite rewrites the specifier. **Fails under SSR** per Vite. This is `react-pdf`’s documented default. |
| Copy `pdf.worker.min.mjs` to `public/` and `workerSrc = '/pdf.worker.min.mjs'` | Unhashed, always `/…` | **Works** in dev and prod; you own version sync. Vite prefers imports over `public/` unless you need a stable name. |
| `workerSrc = '.../node_modules/pdfjs-dist/...'` | Dev-only filesystem | **Breaks production** (no `node_modules` on the CDN). Mozilla helloworld uses this only because it is a local example. |

**TanStack Start implication:** the viewer route should not run this on the server. Vite’s `new URL(..., import.meta.url)` pattern is documented as SSR-unsafe. Set `workerSrc` in client-only code (`ssr: false` on the viewer route, or a `ClientOnly` island). Loader can still return a presigned URL from a server function; rendering is client-side (standing constraint).

### What actually breaks prod vs dev

Documented / first-party mechanisms, not folklore:

1. **Path that only exists in dev** (`node_modules/...` as `workerSrc`) → 404 in production → worker `error` event → **fake worker** or total failure. ([`PDFWorker.#initialize` `terminateEarly` → `#setupFakeWorker`](https://github.com/mozilla/pdf.js/blob/master/src/display/api.js))
2. **Non-string `workerSrc`** (importing the worker module and assigning the namespace) → fake worker. ([PR #17504](https://github.com/mozilla/pdf.js/pull/17504))
3. **SSR / `import.meta.url`** not rewritten → Node file URL or broken relative URL in the server bundle. ([Vite assets docs](https://vite.dev/guide/assets.html))
4. **Two `pdfjs-dist` versions** (app + `react-pdf` nested) → API/worker version mismatch warning. ([react-pdf discussion #1581](https://github.com/wojtekmaj/react-pdf/discussions/1581))
5. **`?worker` without `&url`** assigned to `workerSrc` → type mismatch (constructor vs string).
6. Cross-origin `workerSrc` (CDN): generic build wraps in a blob if origin differs. ([`PDFWorker._createCDNWrapper`](https://github.com/mozilla/pdf.js/blob/master/src/display/api.js)) Prefer same-origin hashed assets from our build.

Vite 8’s bundler is Rolldown ([Vite 8 announcement](https://vite.dev/blog/announcing-vite8)). Worker query suffixes are still in the Vite 8 features page. **Whether Rolldown changes any pdf.js-specific worker edge case is unconfirmed** — we did not run a Vite 8 production build in this ticket.

## 3. Rendering strategy (canvas, long docs, responsive size)

### Canvas per page is the display API

Document → page → viewport → canvas:

```js
const pdf = await pdfjsLib.getDocument({ url }).promise;
const page = await pdf.getPage(1);
const viewport = page.getViewport({ scale: 1.5 });
const outputScale = window.devicePixelRatio || 1;
canvas.width = Math.floor(viewport.width * outputScale);
canvas.height = Math.floor(viewport.height * outputScale);
canvas.style.width = Math.floor(viewport.width) + "px";
canvas.style.height = Math.floor(viewport.height) + "px";
const transform = outputScale !== 1 ? [outputScale, 0, 0, outputScale, 0, 0] : null;
page.render({ canvasContext, transform, viewport });
```

([`examples/learning/helloworld.html`](https://github.com/mozilla/pdf.js/blob/master/examples/learning/helloworld.html); [Examples — Rendering the Page](https://mozilla.github.io/pdf.js/examples/))

HiDPI is **not** automatic: you must multiply backing-store size by `devicePixelRatio` and pass `transform`. CSS size stays at CSS pixels (`viewport.width` / `height`).

**Fit-width (responsive):** compute scale from the container, not a constant:

```js
const unscaled = page.getViewport({ scale: 1 });
const scale = desiredWidth / unscaled.width;
const viewport = page.getViewport({ scale });
```

([Examples — “if you want the canvas to render to a certain pixel size”](https://mozilla.github.io/pdf.js/examples/))

On resize: cancel the in-flight `RenderTask` (`renderTask.cancel()`), then re-`getViewport` + `render`. ([`RenderTask.cancel`](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib-RenderTask.html))

`PDFPageView` in the **viewer layer** is a higher-level page widget (canvas + optional text/annotation layers + rendering queue). It is UI Mozilla asks you not to drop in unmodified. ([Getting Started — layers](https://mozilla.github.io/pdf.js/getting_started/); [`examples/components/pageviewer.mjs`](https://github.com/mozilla/pdf.js/blob/master/examples/components/pageviewer.mjs))

### Virtualization — pdf.js does not ship a React list

pdf.js gives `numPages` and `getPage(n)`. It does **not** virtualize a scrolling list for you. Mozilla’s own viewer uses `PDFPageView` + a rendering queue so off-screen pages are not all drawn at once ([`web/pdf_page_view.js` takes `PDFRenderingQueue`](https://github.com/mozilla/pdf.js/blob/master/web/pdf_page_view.js)). That is viewer-layer code, not a React primitive.

For a custom React viewer:

- Keep **placeholder blocks** for every page (height from `page.getViewport({ scale })` — page 1 is a reasonable first guess; pages can differ).
- `page.render` only for a window around the intersection (current ± N).
- Call `RenderTask.cancel()` when a page leaves the window so work does not pile up.
- Destroy canvases you drop (GPU memory). `PDFDocumentLoadingTask.destroy()` aborts network and destroys the worker when leaving the route. ([`PDFDocumentLoadingTask.destroy`](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib-PDFDocumentLoadingTask.html))

A windowing library (`@tanstack/react-virtual`, etc.) is an implementation detail on top of that; it is not specified by pdf.js.

`react-pdf`: render one `<Page pageNumber={n}>` or map all pages; same memory trap if you mount every `<Page>` for a 400-page spec.

## 4. Per-page visibility → analytics beacon

### What Intersection Observer actually gives you

The observer fires when the **intersection ratio crosses a threshold**, or when `isIntersecting` / `isVisible` flips. Default `threshold` is `0`. Ratio is `intersectionArea / targetArea` (or 0/1 if the target has zero area). Thresholds must be in `[0, 1]`. ([W3C Intersection Observer — `threshold`, `intersectionRatio`, queueing](https://w3c.github.io/IntersectionObserver/))

It does **not** define “this page was read.” There is no dwell-time in the spec. A `threshold` of `0` fires when a single pixel enters the root — useless as a read signal for a tall page.

### A signal we can defend as product, not as a standard

Compose **IO + time in our code**:

1. Observe each page wrapper (the layout box, not the canvas internals).
2. Use `threshold: [0.5]` (or a short list, e.g. `[0.25, 0.5, 0.75]`) so we only care when a substantial fraction of **that page’s box** is inside the scroll root (`root: scroller`, not the viewport, if the viewer scrolls inside a panel).
3. On `isIntersecting && intersectionRatio >= 0.5`, start a **dwell timer** (product choice; IO will not do this). On exit, clear the timer. On timer fire, mark `pageNumber` as viewed in an in-memory `Set`.
4. **Do not** POST on every IO callback. IO can fire many times per scroll.

Dwell duration is **unconfirmed / product** (1s vs 2s vs “max intersectionRatio while intersecting”). Cite IO only for the geometry; cite ourselves for the dwell.

### Batching into a beacon

W3C Beacon: `navigator.sendBeacon(url, data)` queues a **keepalive** POST, prioritized not to fight with rendering, and is the documented way to flush when the page goes background. The spec’s own example coalesces session analytics on `visibilitychange` when `document.visibilityState === 'hidden'`. It explicitly says **do not rely on `unload`** (often does not fire on mobile). No response callback; payload size is capped. CORS: JSON `Content-Type` is not safelisted → CORS mode. ([W3C Beacon](https://w3c.github.io/beacon/))

Recommended flush policy:

- Accumulate page indices (and optional dwell ms) in memory.
- Periodic flush (e.g. every N seconds or every K new pages) via `fetch(..., { keepalive: true })` if we need custom headers / CSRF — Beacon cannot set custom headers. ([Beacon — “does not provide ability to customize the request method [or] custom request headers”; use Fetch + `keepalive`](https://w3c.github.io/beacon/))
- Always flush on `visibilitychange` → `hidden` (Beacon example).
- Deduplicate page numbers in the batch (`Set`) so scroll jitter does not multiply events.

The public viewer’s beacon endpoint is a **server function or server route**, not a TanStack DB collection (standing constraint).

## 5. Text layer — selection/search, and cost

Mozilla’s display API:

- `page.getTextContent()` / `page.streamTextContent()` → `TextContent` (`items[]` of `TextItem` with `str`, `transform`, font). Runs in the **worker**; whitespace normalized to U+0020. ([JSDoc `PDFPageProxy.getTextContent`](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib-PDFPageProxy.html); [`TextContent` / `TextItem`](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib.html))
- `TextLayer` paints those items as positioned `<span>`s into a container, for selection / find / a11y. Extra layout uses a hidden 2D canvas (`measureText`, `--scale-x`). Hard cap: **`MAX_TEXT_DIVS_TO_RENDER = 100000`** then “Ignoring additional textDivs for performance reasons.” ([`src/display/text_layer.js`](https://github.com/mozilla/pdf.js/blob/master/src/display/text_layer.js))

Costs that are in the source, not guessed:

- Extra worker work (`getTextContent` / stream).
- Extra DOM (one span per text run, plus marked-content wrappers).
- Extra canvases in `document.body` for font metrics (`TextLayer.#getCtx`); `TextLayer.cleanup()` only if no pending layers.
- Find-in-page in the **browser** works on those spans; PDF search in Mozilla’s viewer is a separate feature on `textContentItemsStr`.

`react-pdf`: import `react-pdf/dist/Page/TextLayer.css`; `renderTextLayer` defaults **`true`**. Turn it off for thumbnails (`<Thumbnail>` does not render text/annotation layers). ([README](https://github.com/wojtekmaj/react-pdf/blob/main/packages/react-pdf/README.md))

For bitig-flow: enable the text layer on **visible** pages if selection/search matters; skip it on off-screen placeholders. Selection of canvas pixels alone is not text.

CMaps / standard fonts / `wasmUrl` are separate: non-Latin / unembedded fonts need `cMapUrl` + `cMapPacked` (Mozilla pageviewer sets them; `react-pdf` documents copying `pdfjs-dist/cmaps` with `vite-plugin-static-copy`). ([`pageviewer.mjs`](https://github.com/mozilla/pdf.js/blob/master/examples/components/pageviewer.mjs); [react-pdf README — non-latin / cMaps](https://github.com/wojtekmaj/react-pdf/blob/main/packages/react-pdf/README.md))

## 6. Short-lived presigned URL

### CORS is mandatory for `url:`

> If a URL is used to fetch the PDF data a standard Fetch API call (or XHR as fallback) is used, which means it must follow same origin rules, e.g. no cross-domain requests without CORS.

([`getDocument` JSDoc](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib.html))

Garage/S3 must send CORS headers for the viewer origin on GET (and OPTIONS). That is storage config, not pdf.js.

### Two ways to feed the document

`DocumentInitParameters` accepts **`url`** or **`data`** (TypedArray / ArrayBuffer). If TypedArrays are used they are generally **transferred to the worker** (ownership moves). ([JSDoc `DocumentInitParameters`](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib.html))

| Mode | After the ~60s URL dies |
| --- | --- |
| `getDocument({ url: presigned })` | pdf.js **keeps using that URL** for streaming and/or **range** GETs. Later `getPage` / `render` that still need bytes → HTTP error (`Unexpected server response (status) while retrieving PDF "…"`). ([`createResponseError` in `network_utils.js`](https://github.com/mozilla/pdf.js/blob/master/src/display/network_utils.js)) |
| App `fetch(presigned)` → `arrayBuffer()` **while the URL is valid**, then `getDocument({ data })` | No further GETs to Garage for page bytes. Expiry does not affect rendering. Memory: the whole file lives in the worker. |

`onProgress` reports `loaded` / `total` / `percent` during the initial fetch. ([`OnProgressParameters`](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib.html))

### Range + “you may only GET once”

XHR path: if range is supported, pdf.js **aborts the full GET** and issues `Range` requests. Comment in source:

> by cancelling the full request, and then issuing range requests, there will be an issue for sites where you can only request the pdf once. However, if this is the case, then the server should not be returning that it can support range requests.

([`PDFNetworkStreamReader.#onHeadersReceived`](https://github.com/mozilla/pdf.js/blob/master/src/display/network.js))

Fetch path: if streaming is disabled **and** range is supported, it **cancels** the body reader (`"Streaming is disabled."`) and uses range readers instead. ([`PDFFetchStreamReader`](https://github.com/mozilla/pdf.js/blob/master/src/display/fetch_stream.js))

A 60s presigned GET that is aborted and followed by many ranged GETs still needs those later URLs to be valid (same query string, clock still inside expiry). If Garage advertised `Accept-Ranges: bytes`, pdf.js will do that.

**Practical mitigation for ~60s gates:** download once into `data` (disable depending on range is then irrelevant). If files are too large to buffer, keep `url` but **refresh the presigned URL** before expiry (loader / server function) — that refresh protocol is **not** specified by pdf.js.

`disableAutoFetch: true` plus `disableStream: true` limits extra range prefetch; you still need ranges (or a full buffer) for pages the user actually opens. ([`DocumentInitParameters.disableAutoFetch`](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib.html))

## 7. Streaming and HTTP range requests

pdf.js **can** load via stream and via byte ranges. Defaults: `disableRange: false`, `disableStream: false`, `rangeChunkSize: 65536`. ([JSDoc](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib.html))

Range is **enabled only if all** of these hold (`validateRangeRequestCapabilities`):

1. `Content-Length` is an integer.
2. Length **> 2 × `rangeChunkSize`** (otherwise it will not abort-and-range).
3. `disableRange` is false and the URL is HTTP(S).
4. **`Accept-Ranges` response header equals `bytes`**.
5. `Content-Encoding` is `identity` (or missing, treated as identity).

([`src/display/network_utils.js`](https://github.com/mozilla/pdf.js/blob/master/src/display/network_utils.js))

Range GETs send `Range: bytes=begin-end` and expect **206** (XHR also accepts 200 on a range request, per RFC 2616 comment in [`network.js`](https://github.com/mozilla/pdf.js/blob/master/src/display/network.js)). 206 responses must have a `Content-Range` matching `bytes \d+-\d+/\d+`. Range response origin must match the original response origin.

Streaming (Fetch): `response.body.getReader()` chunks into the worker without waiting for the full file. ([`fetch_stream.js`](https://github.com/mozilla/pdf.js/blob/master/src/display/fetch_stream.js))

**Garage:** whether Garage (or the reverse proxy in front of it) sends `Accept-Ranges: bytes`, valid `Content-Length`, identity encoding, and 206 + `Content-Range` is **not** established in this ticket. If it does not, pdf.js simply never sets `isRangeSupported` and downloads the whole object (or fails CORS / 403). If it **does** advertise ranges, see §6 abort-then-range vs one-shot presign.

To force a single GET regardless of headers: `disableRange: true` (and typically `disableStream: false` to still consume the body as a stream). To force a fully buffered load: `disableRange: true` and `disableStream: true`, or pass `data` yourself.

## Recommended shape for bitig-flow

1. **Dependency:** `pdfjs-dist` (Mozilla). Do not add `react-pdf` unless a prototype shows the wrapper shrinking code after we still own virtualization + IO + `data:` loading. If `react-pdf` is added later, do not also depend on a second `pdfjs-dist` version.
2. **Worker (Vite 8 + Start):** in **client-only** viewer code:
   ```ts
   import * as pdfjsLib from "pdfjs-dist";
   import pdfWorker from "pdfjs-dist/build/pdf.worker.min.mjs?url";
   pdfjsLib.GlobalWorkerOptions.workerSrc = pdfWorker;
   ```
   Fallback if `?url` misbehaves under Rolldown: `?worker&url`, then copy-to-`public` as last resort. Never assign a `?worker` constructor to `workerSrc`. Never point at `node_modules` in production.
3. **Route:** mint the presigned GET in a **server function / loader**; `ssr: false` (or ClientOnly) for the canvas/worker island. No TanStack DB collections on this route.
4. **Bytes:** `fetch` the object **immediately** after gate (inside ~60s), `getDocument({ data: new Uint8Array(buf) })`. Treat URL expiry as a loading-phase problem, not a mid-scroll problem. If a file is too large to buffer, that is a follow-up (range + URL refresh); do not assume Garage ranges.
5. **UI:** one canvas per **visible** page; CSS width from container; `devicePixelRatio` backing store; cancel `RenderTask` on hide/resize; placeholder heights for virtualization.
6. **Analytics:** IntersectionObserver `root` = scroller, `threshold: 0.5`, plus a dwell timer; batch page indices; `sendBeacon` or `fetch({ keepalive: true })` on `visibilitychange` → `hidden`, not per scroll.
7. **Text layer:** `TextLayer` (or `renderTextLayer`) on visible pages for selection/search; skip on placeholders. Ship `cmaps` (and standard fonts if needed) as static assets, not a CDN, so the viewer does not depend on unpkg at read time.
8. **Download:** hiding the browser’s download control is cosmetic; the bytes are in the client after `fetch`. Say so in product copy.

## Unconfirmed

- **Vite 8 / Rolldown vs pdf.js worker:** query suffixes and `?url` are documented for Vite 8; we did not produce a production build of this app with `pdfjs-dist` to prove hashed worker MIME type (`text/javascript` vs `application/wasm` mistakes, etc.).
- **Garage HTTP range / streaming quality:** pdf.js’s *requirements* are confirmed; Garage’s *headers and 206 behavior* are not. Sister research may cover this.
- **Exact dwell time and threshold** that should mean “read” — not a pdf.js or W3C definition. `0.5` + ~1s is a starting product rule, not a spec.
- **Whether `react-pdf` 10.4.x will bump off `pdfjs-dist@5.4.296` onto v6** — snapshot is 5.4.296 today.
